# Threat model: omp-memory

## What it protects

A person's own memory: the text in omp's memory banks, the Claude Code memory files, the Codex and claude-mem databases the plugin reads, and the instruction files it counts. That text is
private and can hold credentials, customer data and personal notes. Plus the integrity of the banks: an interrupted or mistaken write must not corrupt a bank or lose native rows.

## Who is trusted

The user account that runs the commands, and root. **A process that runs as that account is trusted completely**: it can already read every bank, every Claude Code memory file, the ledger, the backups
and the configuration, and it can write them. Nothing here tries to stop it, and nothing claims to.

## Who is not, and what stops them

| Risk | What stops it | Residual |
|---|---|---|
| Another account on the machine reads what the plugin writes | The labels, configuration, ledger and importer reports are `0600` in `0700` directories (created by the plugin); backups are made under `umask 077` (`0700` directory, `0600` files) | The banks, Claude Code files and any directory you point `--dest` or `--out` at are as protected as you made them. A backup is a full copy of the memory, so a backup in a shared or synced folder exposes it |
| Memory text leaks through the command's own output | `banks`, `sources`, `labels`, `doctor` and `backup` print counts, bank names, folder paths and file names, not text. The importer's reports name items by key and kind; control characters are removed from every name it prints and a name or front-matter value that looks like a secret is withheld (the item is held). The dry run adds at most three redacted samples of 80 characters per source and type, never of an item with a finding (also in `<out>.samples.json`, `0600`). What the importer prints and writes in reports passes a filter in the importer, and the command line's own output, `--json` and forwarded output pass another (the ledger and the other files that must hold real names are exempt): a bank, folder, label, file name, path or project key that carries a recognised secret is shown only as an index (`bank#3`), in error messages, `--json` and forwarded output too, and a traceback is never printed | Folder paths and memory file names are personal data and are printed (cleaned); files that must hold the real name to work (the state file's directories and bank file names, backup copy names, `MANIFEST.tsv`, folders typed into the configuration) keep it; a secret with no recognisable shape is not caught; a label is whatever you typed. Reports are written through exclusive temporary files and never inside the banks directory, but a file you point `--out` at is as protected as you made it |
| A secret in a memory is copied into a bank | Redaction by the Hindsight proxy's rules, then omp's own memory redaction, then the **HOLD** stage: an item with a remaining password assignment, credential pair, private key, bearer token, token prefix, credential in a URL or long token beside a key name is **held back**, listed by key and kind, and imported only after you name its key with `--release-held` | Pattern matching cannot see a secret without a recognisable shape (a bare password in prose, a split or encoded secret). Read the dry run; release only what you reviewed. Rows already in a bank are not re-scanned |
| An import damages a bank | `import --apply` refuses without a dry run of the same options and, when it writes into a bank that already holds anything of yours, a verified backup of the banks, both from the last 24 hours (`--no-backup` and `--skip-dry-run-check` are the explicit escapes, and say so). Which banks it reaches, and whether the plan changed since you read it, is judged from a plan made when `--apply` runs. The importer refuses a bank another process has open (best effort: `lsof`, or `/proc` of your own user on Linux; checked before the plan, before each bank's write and before each undo deletion; `--force-closed` is the only bypass and warns), a bank directory, database or side file that is a symbolic link, a library that is not exactly omp's version (no override; every SQL statement it relies on must also be in the package and, when the omp binary can be scanned, in it, and the library must pass a write test in a scratch bank: the importer's exact write sequence, checked step by step), a bank whose schema (tables, full trigger definitions, no extra trigger or view) differs from a fresh library database, and a bank with more than one embedding model. Embeddings are made first; rows, annotations and embeddings of a bank are then one transaction, so a failure or kill leaves nothing or everything; native rows are never touched (the write is rolled back if their count or a digest of their content changes). A second `--apply` import or undo is refused while a lock file beside the ledger names a live process. `verify` compares row ids and provenance with the ledger; `undo --run` removes only rows that are provably the importer's, reports others, and updates the ledger only for rows really gone | A process that opens a bank in the instants between the check and the write (omp starting a session during the import), and a link made between the symlink check and the library's own open: close sessions and keep them closed. A bank written by a newer omp that happens to keep the same schema. Rows written by an earlier build of the importer without embeddings are reported by `verify` and removed by `undo --run`, not repaired |
| A mistaken or malicious value in the configuration runs the wrong program | The configuration file is refused when it is a link, not yours, writable by group or others, has an unknown key, or a path with `..`; a configured `bun` is used or refused, never replaced by another; `set` of `bun` and `ompBin` checks that they exist | The environment: whoever controls your shell controls `OMP_MEMORY_BUN`, `OMP_BIN`, `OMP_MEMORY_LIB_DIR` and `OMP_PLUGINS_DIR`. **The library directory is code that the importer runs**: `omp-memory setup` installs only the exact npm version of omp's own package (and its pinned dependencies), but a directory you point `libDir` at is trusted as written |
| A changed vendored file runs in your name | `vendor/SOURCE.sha256` records every vendored file; `doctor` fails when one differs; the tests fail when `vendor/` differs from the source tree it was copied from (when `OMP_MEMORY_SOURCE_DIR` names it) or from the record | Someone who can write the install directory can edit the record too (out of scope: they run as you) |
| Writing outside where it documents | The plugin writes only the files in the README's table. Every path from configuration must be absolute (or `~/`-relative) and have no `..`; a path on the command line may also be relative and is made absolute against your directory before the importer (which always starts in the plugin's own directory, never yours, so a `bunfig.toml` or `.env` in your directory is not read) gets it; the launcher and the scripts take no path from the network. The restore drill only ever creates and deletes its own private directory | A path you give is used as written, and you can point it at something you should not (the importer refuses report files inside the banks directory or over a file that is not an earlier report) |
| A stale or wrong label | Labels live only in the labels file; they never touch a bank, and `labels set` refuses an unknown bank, a duplicate (case-insensitive) and a label outside 1 to 60 characters or with a control or bidirectional character | A label is shown as typed |
| Contacting a network | Nothing does, except what the README's Network section lists: `omp-memory setup` (the npm registry, then omp's embedding runtime from npm and its model from huggingface.co, once, because you ran it; on Linux x64 the `onnxruntime-node` install script also fetches CUDA binaries from GitHub unless you set `ONNXRUNTIME_NODE_INSTALL_CUDA=skip`), omp's library downloading that runtime and model during `import --apply` when they are not cached, and the optional `export-hindsight --apply` reaching your own Hindsight. A registry address with credentials is refused | Those, and whatever `ssh`, `bun add` and the packages' own install scripts do: `bun add` runs with your whole environment (HOME, PATH, proxy and token variables, any cloud credentials in it) and the install scripts of the packages it trusts can read all of it. `NOTICE` lists every package `setup` fetches, with its license. Nothing verifies those packages beyond the npm registry's own integrity checks and the exact version pin |

## Out of scope

- **Shell scripts and `ssh`.** The backup, restore and export scripts and the optional remote export command run as you and are not sandboxed; the remote command is whatever you name.
- **Memory text you pass to an agent.** The skill tells an agent to work from counts and keys; a file name or a Hindsight tag is still data from a file someone wrote, printed after cleaning, and an agent that reads reports should treat it as data, not instructions.
- **Root, and other processes that run as you.** They can read the banks, the Claude Code memory files, the ledger, the backups and the configuration, and write any of them.
- **Shared machines.** Another account that can read your home directory, a shared backup directory or `/tmp` while a restore drill runs (the drill's scratch directory is `0700`, but its name is predictable in kind) is not defended against.
- **Memory you chose to keep.** A secret that redaction and the HOLD stage did not recognise, and that you released or did not notice, is in a bank in plain text, as it was in the source.
- **The npm package and its dependencies, Bun, SQLite, `lsof`, ssh.** The importer runs the library that `setup` fetched (or the one you point it at) on the Bun you point it at; their flaws are theirs.
- **The extent of omp's own handling.** After an import the rows are ordinary omp memory: omp recalls them into prompts, and omp's own consolidation and deletion rules apply.
- **Audit status.** Not audited by a third party; the guards above are covered by the plugin's own tests.
